# Minecraft 自主玩家：第一版顶层设计

版本：v0.1  
日期：2026-10-17  
阶段：目标架构设计，尚未完成实现选型与端到端验证

后续细化：[客户端接入与核心合同 v0.1](minecraft-agent-client-bridge-contracts-v0.1.md)。该文细化字段来源、输入边界、模型工具协议与判别实验，不代表接入候选已经验证或获选。

运动专项细化：[动作原语、导航与恢复 v0.1](minecraft-agent-motion-navigation-recovery-v0.1.md)。

## 1. 设计结论

本项目建设一个长期自主运行的 Minecraft 玩家运行时。真实 Java 客户端是唯一身体；通用模型通过工具获取证据、选择目标和提交行动意图；本地运行时持续控制身体、核对结果并处理恢复。

**结构化观测优先，视觉按需补充；模型工具调用是决策接口，不是逐帧运动协议。** 模型可以选择不同动作粒度，但不能绕过状态、控制权和执行生命周期。

目前最重要的未验证点不是模型选型，而是：**在不安装客户端 Mod、不修改服务器的条件下，怎样从同一个真实玩家获得足够可靠的结构化观测，并将其与输入执行、必要截图关联。** 本设计把它作为必须验证的接入条件，不假称已有一个现成接口。

## 2. 已确认范围与约束

- Minecraft Java 版，原版玩法多人服务器，可能存在认证插件。
- 仅普通玩家权限；不依赖管理员、RCON、服务端插件或服务端专用接口。
- 不使用客户端 Mod；运行真实 Minecraft 客户端进程。
- 允许使用普通客户端可获得的结构化信息；不要求纯视觉键鼠。
- 视觉不是第一观测通道，不逐动作调用模型分析截图。
- 使用 OpenAI Chat Completions 和 Anthropic Messages API；不依赖自训练或本地专用模型。
- 长期自主活动，支持聊天、人类控制台消息调整方向、自动重连和死亡恢复。
- 目标服务器已开启死亡不掉落；重生后仍重新观察背包与位置。
- 支持离线身份和进入服务器后的注册、登录；正版身份登录预留，首期不实现。
- 动态生成和执行代码保留在目标架构，不要求首个大版本开放。
- 以长期能力和维护性设计，不按开发工期缩减目标；版本演进按依赖与证据排序。

不擅自加入的能力：进程内存读取、运行时注入、Java Agent、第二个玩家辅助观测、服务端遥测。它们不能因为技术上不叫 Mod 就被视为已经允许。

## 3. 研究依据与采纳原则

依据前期研究交接包及六份专项报告：World State/Spatial Memory、执行 Runtime、学习型控制、Mineflayer 审计、身体后端、导航与运动控制。本次设计未搜索外部资料，也未独立复现报告中的仓库或性能结论。

采纳：

- 路线规划、运动控制、技能执行和目标决策分离。
- 当前观测、客户端预测、历史记录、推断和未来预测分离。
- 控制器能力参与动作可行性判断。
- 唯一行动提交边界、控制代次、取消和结果核对。
- 局部失败局部恢复，事件触发加周期检查兜底。
- 知识、空间记忆、情景记忆和技能分别管理生命周期。

不直接采纳：

- “换寻路库能解决三分之一问题”等缺少样本分布的比例。
- 客户端结构化状态等于逐帧服务器权威状态。
- 同一 tick 回调意味着截图和状态天然同步。
- 禁止使用跨会话的真实观察记忆。
- 某组 Baritone 开关足以保证完整的信息边界与控制合同。
- 训练环境成功率可以推导真实多人服务器能力。
- 普通 API 输出动作序列等于实现了 RTC 论文算法。

报告的版本、分支和证据强度不完全一致。具体依赖在实现阶段重新固定版本；研究中的本地探针文件未随报告完整交付，不能视作本项目的复现产物。

## 4. 身体接入：一个客户端、一个玩家、一条证据链

### 4.1 目标形态

```text
真实 Minecraft 客户端 ←→ 服务器
       ↑ 输入执行             
       ↓ 可获取观测
本地 Client Bridge
       ↕ 版本化本地协议
Agent Runtime ←→ 模型 API
```

Client Bridge 是能力边界名称，不代表必须安装 Mod。它组合本地输入、画面采集、日志以及经验证的协议观测能力。

### 4.2 接入候选与实际限制

| 通道 | 用途 | 状态与限制 |
|---|---|---|
| 系统键鼠输入 | 移动、视角、交互、界面和聊天 | 主输入候选；必须处理焦点、按键释放、鼠标捕获和界面状态 |
| 同一连接的本地协议代理 | 区块、实体、背包更新、生命、聊天等结构化证据 | 首选验证候选，不是已确定实现；需要测试登录、压缩、版本和透传兼容 |
| 客户端日志 | 连接、异常、部分消息 | 辅助来源，不是完整状态接口 |
| 原版界面/调试界面 | 按需读取普通玩家可见信息 | 需要打开界面并可能改变交互上下文 |
| 窗口截图 | 场景确认、未知界面、异常诊断 | 按需及事件触发，不是逐 tick 模型输入 |

本地协议代理不需要修改服务器。它只在同一客户端连接上观察已交换的信息，不能自动获得客户端内部速度、碰撞结果、界面焦点或逐帧服务器确认。现代协议的认证、加密与版本差异可能限制可观测性，必须以目标环境验证。

**代理优先作为观察通道，不默认注入游戏动作包。** 真实客户端继续通过正常输入路径产生动作，避免客户端与代理形成两个独立行动写入者。

若代理无法提供足够状态，不静默降级成纯视觉项目，也不擅自加入注入方案。应明确列出不可获取字段、受影响能力和可选替代，再决定接入路线。架构其他部分可以先按能力合同设计。

### 4.3 Mineflayer 和 Baritone 的位置

- Mineflayer 独立登录不是正在截图的那个玩家，不能直接充当真实客户端控制桥。
- 可评估复用协议解析、版本数据和部分物理组件，不要求创建第二个 bot 连接。
- Mineflayer Pathfinder 作为基线和源码参考，不作为导航核心依赖。
- Baritone 的动作图、分段规划和执行状态机值得借鉴；不安装客户端 Mod 的路线不直接运行其客户端模块。
- 不建立视觉重建主链路；需要视觉时采集真实客户端画面。

## 5. 责任结构

```text
控制台消息 / 游戏聊天
          ↓
消息入口与来源识别
          ↓
目标与承诺管理 ←→ 通用模型工具循环 ←→ 上下文与证据检索
          ↓             ↑
计划提交与执行协调 ← 进展/异常监测
          ↓
技能执行器 / 导航 / 动态代码 Worker
          ↓
控制资源仲裁与本地 Motor
          ↓
动作网关 → Client Bridge → 真实客户端

Client Bridge → 观测归并 → World State
                            ├→ Motor 局部视图
                            ├→ Skill 执行视图
                            └→ Planner 摘要
                                  ↕
                     Knowledge / Spatial / Episodic / Skills
```

这些是模块责任，不是要求每层成为服务。Planner、Sentry 和对话可以使用同一模型，通过不同调用上下文承担不同职责。

模型提出计划；执行协调器接受、拒绝或修订提交。所有模块不能各自维护一套独立的“当前任务真相”。

## 6. 模型 API 与工具调用

### 6.1 提供方边界

实现 OpenAI Chat Completions 与 Anthropic Messages 两个适配器。业务层使用统一的消息、图像引用、工具 schema、结构化决策与结果格式；提供方差异留在适配器中。

能力声明包括图片输入、工具调用、流式传输、结构化输出及限制。不同模型实际支持项启动时校验，不假定兼容端点完整实现所有功能。

### 6.2 工具分类

| 类别 | 工具示例 | 语义 |
|---|---|---|
| 当前状态 | `observe_state`, `inspect_inventory`, `inspect_execution` | 返回带时间、来源、未知字段的快照 |
| 按需视觉 | `capture_view`, `inspect_screen` | 获取真实画面，说明采集时间与界面状态 |
| 证据检索 | `query_places`, `query_knowledge`, `retrieve_episodes` | 返回历史或规则证据，不冒充当前观察 |
| 目标管理 | `propose_goal`, `revise_plan` | 带预期目标版本，执行协调器提交 |
| 技能执行 | `start_skill`, `cancel_execution` | 返回执行 ID，后续通过反馈和结果观察 |
| 身体动作 | `propose_action_chunk` | 有限时、带前提的低层提案，仍受统一仲裁 |
| 社交 | `send_chat`, `reply_to_player` | 有收件对象、去重标识与发送状态 |

工具名是概念示例，正式 schema 在下一阶段定义。`inspect_inventory` 不保证随时能读取完整背包；不可得时返回 unknown，并可建议打开界面观察。

### 6.3 正常模型循环

1. Runtime 组织当前目标、状态变化、重要消息与执行反馈。
2. 模型按需查询结构化状态、知识或记忆。
3. 信息不足且视觉有帮助时请求截图。
4. 模型选择技能或提交短时动作提案。
5. Runtime 校验并返回 execution ID 或拒绝原因。
6. 本地技能持续执行；完成、停滞、异常或人类改向时产生新决策事件。

无需每次移动调用模型，也无需每次工具调用截图。长技能不占住一个无法取消的模型请求。

### 6.4 模型请求可靠性

- 请求关联目标版本、执行代次和观测引用。
- 流式工具参数完整结束并通过 schema 后才可提交。
- 模型调用重试与游戏动作重试分离；工具提案使用本地幂等标识防止重复提交。
- 相关状态改变后重新核验输出，不因无关区域更新而丢弃所有结果。
- 提供方切换从规范上下文重新构建请求，不依赖厂商私有会话状态。
- 调用优先级：即时异常与人类调整优先，后台总结最低；设并发、token、费用与重试预算。
- 记录输入证据、输出决策和工具结果，不要求模型暴露内部思维链。

## 7. 自主性与人类介入

Goal Manager 保存持续偏好、当前目标、子目标依赖、资源预算以及对玩家的承诺。模型可以自主提出探索、补给、建设和协作目标；接受目标后建立可检验里程碑。

控制台消息代表人类方向调整，不等于人类逐帧遥控。新消息可以修改优先级、暂停目标或要求返回。游戏聊天参与正常交流和合作，但来源权限不自动等同控制台。

Sentry 首先由确定性检查组成：进展、前置条件、生命需求、执行期限、反复失败、连接健康。语义异常可以调用模型。事件之外保留周期复核，避免漏事件造成永久停滞。

目标评价不能只看“产生了多少动作”。探索获得新信息、交付承诺完成、材料到位和实际建筑变化都可成为进展证据。

## 8. World State 与观测调度

### 8.1 当前状态不是全知世界

World State 是规范读取入口。观测归并器拥有当前状态写入权；模型、技能和记忆不能直接写入“观察事实”。

每个重要字段保留：值、来源、采集时间、接收时间、会话、维度、版本、有效性和证据引用。类别区分 observed、predicted、inferred、historical、unknown、conflict。

客户端发出的移动坐标是本地报告，不是服务器明确确认。服务器位置修正是独立证据；没有修正不能直接解释为逐帧确认。

身份包括 serverProfile、worldGeneration、dimension、connectionEpoch、bodyEpoch。服务器地址不等于永久世界身份。身份不确定时隔离旧地图，但仍可使用当前局部观察维持活动。

### 8.2 三种读取视图

- Motor：内存中的近身姿态估计、碰撞与支撑信息、当前动作阶段、有效期限。
- Skill：物品、目标、局部路线、前置条件、进展和副作用状态。
- Planner：摘要、变化、失败原因、待解决目标及带来源的检索证据。

数据缺失时显式返回 unknown，不能为了让接口好用而填入假精度。

### 8.3 视觉调度

截图触发包括未知界面、观测冲突、模型主动查看、复杂目标辨认、执行停滞和关键结果检查。必要时可以采集短图像序列，但不把截图变成所有动作的固定前置条件。

截图与结构化状态使用时间范围、相机估计和会话关联；不声称原子同帧。观测队列有界，过时画面不无限排队。

结构化可得不等于可以任意利用：隐藏矿石、遮挡实体不能经地图、工具或记忆间接泄露给决策。实际观察过的信息可以长期记忆，重新使用时标记历史与验证要求。

## 9. 导航与身体控制

### 9.1 四个责任

1. 地点路线：区域、入口、已知通道和探索边界。
2. 局部动作规划：在当前几何与资源条件下生成动作边。
3. 动作可行性：检查当前控制器、起始姿态、观测充分性和风险。
4. 本地执行：持续纠偏、阶段推进和结果核对。

动作边不是相邻方块坐标，而是 WALK、STEP_UP、JUMP、SWIM_UP、SHORE_EXIT、CLIMB、OPEN、DIG、PLACE 等受条件约束的转移。未知空间不能当空气。

控制器能力清单声明支持的模式、初态范围、终态条件、资源、观测依赖、版本、取消方式和验证记录。未测试的成功率为 unknown，不填写虚构置信度。

### 9.2 确定性控制为基础

普通行走采用闭环跟踪；跳跃、游泳、攀爬、搭桥和交互采用各自的小型状态机。例如搭桥：靠近边缘、保持支撑、瞄准合法面、放置、核对、前移。

可以使用确定性短程物理推演评估候选动作，不需要训练模型。复杂 MPC 只有在预测误差和收益得到验证后引入。

模型可提出短时动作片段，但片段必须带起始状态范围、期限、终止条件和当前执行阶段。禁止迟到方案硬切跳跃相位，禁止按键序列盲播到结束。

### 9.3 时序合同

区分服务端 tick、客户端 tick、观测到达、动作提交和模型推理。无 Mod 时不能假定能订阅精确客户端 tick；接入层需声明是直接可观测、估计还是未知。

使用单调时间期限与经测量的本地调度。20Hz 可作为初始实验点，不是硬实时保证；高于游戏结算频率的提交也不自动提高效果。

API 中断时执行有效技能的有限部分；到达决策边界后稳定或进入模式特定恢复。水中保持呼吸与平地停步是不同动作。

### 9.4 防止恢复振荡

失败按控制器版本、地形特征、服务器条件和证据范围记录。局部纠偏、技能换路、目标重规划逐级升级。每级有重试预算、冷却、最低进展和重复状态签名；没有新证据不反复执行同一失败方案。

搜索返回部分路径时，执行终点必须可停稳或有明确保持行为。搜索超时不等于目标不可达。

## 10. Skill 执行合同与控制权

Skill 是合同与版本化资产，可由人工代码、状态机、模型引导流程或后续生成代码实现。

最低合同：参数、前置条件、能力与资源、进展信号、成功谓词、终止条件、取消方式、可能副作用、恢复方式和验证记录。

运行状态、失败原因、结果确定性分别存储。timeout 不等于未执行；目标已满足也不证明副作用由自己造成。

资源按移动、视角、手持物、界面、交互和聊天发送划分。真实键鼠后端里聊天输入会争用焦点和键盘，不能沿用协议后端“聊天与移动天然并行”的假设。复合资源请求原子准入，默认不允许两个控制器同时写同一输入。

每个命令携带连接代次、身体代次、资源 owner 代次和期限。动作网关在实际输入提交前再次校验。旧回调和旧 finally 不得释放新 owner 的资源。

正常切换允许旧控制器在受限权限下完成交接动作；紧急切换先撤权，再由明确的恢复控制器接管。不能撤销全部执行权后又指望旧控制器继续维持上浮或落地。

墙钟看门狗独立检查期限。客户端线程或系统输入通道冻结时无法保证立即改变身体，外部监督应标记控制丢失并执行恢复；恢复后先清理过期输入再继续。

## 11. 副作用、认证与恢复

### 11.1 副作用核对

对放置、挖掘、合成、容器转移、聊天和指令保存必要意图与结果证据。发送与本地落盘不可能和服务器原子提交，不承诺 exactly-once。

结果未知时先核对当前世界，禁止盲目重放。核对不确定只阻塞相关依赖，不能阻止逃离危险或其他无冲突任务。

建筑等长操作采用有界分段意图、逐步验证和阶段检查点，不逐帧 fsync，也不等全部完成才记账。

### 11.2 认证

连接身份与服务器内认证分开。当前离线身份；未来正版身份使用独立适配器。

模型理解服务器提示并提出流程，凭据模块按服务器档案和身份绑定填入敏感参数。命令形式不写死为唯一模板。实际输入认证命令时，画面、轨迹和聊天日志也可能包含密码，必须对采集和存储链路做屏蔽。

普通玩家伪造的提示不自动触发凭据发送；证据不足时停止提交并求助。未知验证码或外部认证不能靠无限尝试解决。

### 11.3 恢复顺序

断线、死亡、进程退出或维度改变后，废止旧控制权，重新接入与认证，核对身份、位置、背包和未决效果，再恢复目标与检查点。恢复不重放旧按键，也不恢复任意脚本调用栈。

重连有退避和失败状态。连接级恢复失败或客户端健康异常时才升级到重启进程。

## 12. 长期数据与动态技能

| 数据 | 职责 | 生命周期要点 |
|---|---|---|
| Knowledge | 配方、机制、服务器规则 | 版本与适用范围、来源、反例、替代关系 |
| Spatial Memory | 地点、路线、资源观察、危险与探索边界 | 世界隔离、最后核实时间、变化和再验证 |
| Episodic Memory | 任务经过、失败原因、合作经历 | 事实与解释分开，摘要可追溯原始证据 |
| Skill Assets | 执行方法与适用条件 | 不可变版本、验证、降级、撤销 |
| Prospective Tasks | 对玩家的承诺及未来任务 | 期限、依赖、履行与取消 |

规则查询、空间检索、错误索引和语义检索分别使用适合的数据结构。先按世界、版本和适用条件过滤，再进行相似度排序。

推荐内存热状态、SQLite 事务元数据、分块压缩地图/轨迹文件及可重建全文或向量索引。索引不是事实源。

知识修正先建立反例，区分执行缺陷、环境变化与规则错误，验证后局部修订，不能一次失败就推翻全局规则。

动态代码阶段：草稿、检查、隔离测试、有限试运行、启用、降级或撤销。生成代码只能使用能力接口，不持有客户端、密钥、原始 socket 或核心状态写入权。运行实例冻结技能版本；撤销代码不能撤销已经发生的世界变化。

## 13. 工程组织与可维护性

建议单仓库、模块化 Runtime，初始语言候选 TypeScript；最终依赖以协议桥实验为依据。不为假设的未来扩展引入多语言和分布式基础设施。

```text
contracts/          版本化领域合同与消息 schema
client-bridge/      输入、协议观测、日志、截图适配
world-state/        证据归并、快照、局部视图
execution/          控制权、生命周期、副作用与恢复
navigation/         地点路线、局部动作图、可行性
controllers/        本地动作原语与模式状态机
skills/             技能资产与执行器
agent/              目标、对话、模型工具循环
providers/          OpenAI、Anthropic 适配器
memory/             知识、空间、经历与检索
persistence/        数据事务、迁移与归档
diagnostics/        轨迹、故障切片与指标
evaluation/         合同测试、场景与故障注入
```

建议隔离真实客户端、Runtime 与动态代码 Worker；输入期限检查不应被模型请求或搜索计算阻塞。具体独立进程数量留给接入原型，不按模块数量拆服务。

领域对象不暴露第三方 bot 类型。模型供应商 SDK 不进入控制器，数据库对象不进入 Motor，技能不直接调用输入库。公共接口有 schema 版本和契约测试。

观测高频队列可合并，关键生命周期事件可靠处理；任何队列必须有容量和过载行为。日志与截图设置保留周期，避免长期运行无限增长。

## 14. 演进与验收

### 阶段 0：身体接入判别实验

这是后续实现的前置验证，不是重新做广泛论文研究。

- 同一个真实客户端能否获得所需结构化协议更新。
- 离线连接与服务器内认证能否透明完成。
- 系统输入是否可靠到达正确窗口，焦点和鼠标捕获能否识别。
- 移动报告、服务器修正、画面与输入如何关联。
- 客户端 tick、姿态、界面和背包字段哪些直接可得，哪些需要推断。
- 验证没有第二个玩家或第二个独立游戏写入者。

交付字段可用性矩阵、时序记录和接入决策。不满足结构化优先要求时，明确架构缺口，不伪造完成。

### 阶段 1：执行与状态基础

连接、认证、World State、工具接口、输入网关、取消、死亡和重连。旧代命令拒绝、凭据不进入普通日志、异常后不重放按键。

### 阶段 2：动作原语与导航

行走、视角、基础交互、跳跃、游泳及上岸逐项验证。记录规划认为可行但实际失败的比例；未知不当空气，失败能定位到图、控制或状态。

### 阶段 3：长期自主生活

采集、合成、补给、探索、空间记忆、任务持续推进、聊天和控制台改向。验证断线、死亡、世界改变和 API 暂不可用。

### 阶段 4：复杂行为与动态技能

建造、战斗、复杂地形、多粒度动作、代码生成与技能晋升。能力逐场景扩展，不用一个总成功率掩盖弱项。

所有阶段持续记录：模型与观测延迟分布、有效动作延迟、卡键、控制撤权、重复副作用、恢复循环、未决操作积压、内存与日志增长、人工介入率。性能阈值通过目标环境实验确定。

## 15. 必须保持的不变量

1. 同一真实玩家的观测和行动绑定同一身体会话。
2. 所有 Agent 行动经过统一动作提交边界；客户端自身的正常协议行为不等于第二个 Agent 执行者。
3. 旧连接、旧身体、旧控制权命令不能继续执行。
4. 未知、预测和历史不能冒充当前观察。
5. 结果未知不能自动解释为未执行并重放。
6. 模型工具调用不能绕过生命周期、资源和前置条件。
7. 恢复的是目标与已验证检查点，不是原始按键或任意调用栈。
8. 缺少观测时明确缩小能力，不通过虚构字段保持接口表面完整。
9. 当前不依赖训练模型；本地控制与确定性模拟不受此限制。
10. 视觉是可请求的真实证据，不是每步强制输入，也不是重建数据的重复证明。
