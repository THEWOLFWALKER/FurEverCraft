## A. 核实结论、证据等级与阻塞项

**本次解决了上一轮最主要的阻塞：确实找到了并读取了 `misode/mcmeta` 的 26.3 标签、完整 commit SHA、目录及真实文件。** 可以以 mcmeta 的 `26.3-data` 配方 / tag / 掉落为第一批 vanilla 源，以 `26.3-summary` 的默认物品组件为补充，以 `26.3-registries` 为实体集合核对。不是仅从 README 的标签命名规则推断它们存在。

### A2. 当前真正的阻塞

1. **没有 vanilla 全量可操作语义的验收证明。** 已验证样本、特定注册表集合、Git tree 文件计数，尚未逐个读取并校验所有配方、tag、掉落与物品组件，不应宣传“26.3 100% 完整知识库”。
2. **minecraft-data 的 26.3 候选仍处于 PR。** #1300、#1301 本次读取时均为 open。其自述的“经过实际服务器测试”是 PR 作者的报告，不是本次测试结论；其 schema / 数据可用于对照，不能代替 mcmeta 的源级证据。
3. **继承类别需要专门证明。** 例如候选 `blockLoot=pc/26.2`、`effects=pc/26.1`、`mapIcons=pc/1.20.2`。不同类别要分别做 26.3 差异检验；只看 API 版本参数 `26.3` 会误导。
4. **非完整行为数据。** 静态配方能证明材料与输出，但不能单凭它推出容器交互细节；静态掉落条件不能证明当前装备/运气/方块状态是否满足；默认物品组件不是实时背包物品的完整组件快照。
5. **权利/分发许可边界未自动解决。** mcmeta 整理的 Minecraft 游戏内容与该项目的代码许可不是同一件事；见 F。

### A3. 禁止冒充已验证的事项

- 不从 `26.3-<branch>` 的**命名惯例**推定文件存在；本报告仅将确实返回的 Git ref 和实际读取的样本列为已核实。
- 不将 `mcmeta` 的 `summary` 当作 datapack 原始目录；**它是整理后的摘要**。
- 不将 GitHub 文件的 `sha`（Git Blob **SHA-1**）写进 SHA256 字段。
- 不将 `minecraft-data` 的 `protocolVersions.json` 与 `data/dataPaths.json` 混为一谈。
- 不将 PR `open` 的 head 内容写作 `master` 已合并。
- 不将 tag / recipe 的已见实例外推为所有引用均可解析。

**关键 JSON 片段与字段解释：** 以下都是从上述已读取真实文件中摘取或作保字段投影，非新造配方。样本覆盖的类别对应表中 `用途`。

**① 有序配方、引用物品 tag：`recipe/chest.json`**

```json
{"type":"minecraft:crafting_shaped","key":{"#":"#minecraft:planks"},"pattern":["###","# #","###"],"result":{"id":"minecraft:chest"}}
```

`key` 的对象键 `"#"` **只是图案占位符**，`"#minecraft:planks"` 这个字符串前缀 `#` **才是物品 tag 引用**。三行每行 3 格，中间空槽；解析器不能删除内部空位。

**② 无序配方：`recipe/oak_button.json`、`recipe/yellow_dye_from_dandelion.json`**

```json
{"type":"minecraft:crafting_shapeless","ingredients":["minecraft:oak_planks"],"result":{"id":"minecraft:oak_button"}}
```

`ingredients` 是无序且**有重数**的材料序列；不同的 `group` / `category` 属于配方元数据，不是额外原料。`yellow_dye_from_dandelion.json` 另行确认 `ingredients:["minecraft:dandelion"]` → `minecraft:yellow_dye`。

**③ 使用 tag 且重复两次：`recipe/mushroom_stew.json` + `tags/item/mushrooms.json`**

```json
{"ingredients":["#minecraft:mushrooms","#minecraft:mushrooms","minecraft:bowl"],"result":{"id":"minecraft:mushroom_stew"}}
```

```json
{"values":["minecraft:brown_mushroom","minecraft:red_mushroom","minecraft:shelf_mushroom"]}
```

**两个相同 tag 是两个材料槽位，不是重复数据。** `#minecraft:mushrooms` 指向 tag 类型为 **item** 的 `minecraft:mushrooms`。官方 26.3 说明新增 Shelf Mushroom 并确认可用于炖汤，同时明确允许“任意两种蘑菇”作为原料，这与两个 tag 项吻合。参见[官方发布说明](https://www.minecraft.net/en-us/article/minecraft-java-edition-26-3)。

**④ 加工：`recipe/baked_potato.json`**

```json
{"type":"minecraft:smelting","category":"food","cookingtime":200,"experience":0.35,"ingredient":"minecraft:potato","result":{"id":"minecraft:baked_potato"}}
```

`cookingtime` 是游戏刻数；`experience` 是经验收益相关数据；**不能从这个文件推出适用燃料列表**，也不能将它误读为 `campfire_cooking` 或 `smoking`。

**⑤ 嵌套 tag：`tags/item/logs.json`、`logs_that_burn.json`、`poplar_logs.json`**

```json
{"values":["#minecraft:logs_that_burn","#minecraft:crimson_stems","#minecraft:warped_stems"]}
```

`logs_that_burn.json` 中实际含 `"#minecraft:poplar_logs"`；`poplar_logs.json` 中有 `"minecraft:poplar_log"`、`"minecraft:poplar_wood"`、`"minecraft:stripped_poplar_log"`、`"minecraft:stripped_poplar_wood"`。应当**递归展开**，保留来源链路并做 cycle / missing 保护。`logs_that_burn` 与 `poplar_logs` 已读取；其余嵌套引用**本次未逐个读完**，不可宣称整个 tag 图已闭合。

**⑥ 复杂掉落和 predicate：`loot_table/blocks/oak_leaves.json` + `predicate/tool/can_shear.json`**

```json
{
  "type":"minecraft:block",
  "pools":[{
    "entries":[{"type":"minecraft:alternatives","children":[
      {"type":"minecraft:item","condition":{"type":"minecraft:any_of","terms":["minecraft:tool/can_shear","minecraft:tool/can_silk_touch"]},"name":"minecraft:oak_leaves"},
      {"type":"minecraft:item","condition":{"type":"minecraft:all_of","terms":[{"type":"minecraft:survives_explosion"},{"type":"minecraft:table_bonus","enchantment":"minecraft:fortune","chances":[0.05,0.0625,0.083333336,0.1]}]},"name":"minecraft:oak_sapling"}
    ]}]
  }]
}
```

以上**仅为第一个 pool 的保字段投影**，原件 3,208 字节、含其他 pools，不能将此投影替代完整 JSON。`minecraft:tool/can_shear` 不是 `#minecraft:tool/can_shear` tag；是另一个 predicate 文件引用，实际读取内容为：

```json
{"type":"minecraft:match_tool","predicate":{"items":"minecraft:shears"}}
```

`any_of`、`all_of`、`survives_explosion`、Fortune 的 `table_bonus` 会影响候选掉落。**查询默认返回条件 AST/文本解释，不要不经求值就报告“必掉橡树苗”。**

**⑦ 26.3 官方新增：`recipe/straw_bed.json`、`recipe/poplar_planks.json`、`recipe/white_cushion.json`**

```json
{"type":"minecraft:crafting_shaped","key":{"X":"minecraft:hay_block"},"pattern":["XXX"],"result":{"count":4,"id":"minecraft:straw_bed"}}
```

官方 26.3 明确 **3 Hay Bales → 4 Straw Beds**；文件与官网一致。这个例子还证明：**草床并不是普通床的重生点语义替代品**；其特殊用途必须有规则说明来源，不能仅由 recipe 推断。

```json
{"type":"minecraft:crafting_shapeless","ingredients":["#minecraft:poplar_logs"],"result":{"count":4,"id":"minecraft:poplar_planks"}}
```

`poplar_planks` 引用 `#minecraft:poplar_logs`，实际 item tag 文件已打开，4 个白杨原木类物品都在其中。`white_cushion.json` 为三格 `minecraft:white_wool_slab` 的 `crafting_shaped`；这也说明新增内容可以依赖另一个新增配方，不应只按旧版百科推依赖。

**⑧ 默认物品组件：`26.3-summary/item_components/data.json`**

从已完整读取的文件解析键 `baked_potato`、`straw_bed`，**摘录**：

```json
{
  "baked_potato": {
    "minecraft:food": {"nutrition": 5, "saturation": 6},
    "minecraft:consumable": {},
    "minecraft:max_stack_size": 64
  },
  "straw_bed": {
    "minecraft:item_model": "minecraft:straw_bed",
    "minecraft:item_name": {"translate": "block.minecraft.straw_bed"},
    "minecraft:max_stack_size": 16
  }
}
```

以上**不是这两项的全部组件**。默认组件是**原版默认物品定义**，而不是“玩家当前物品栈组件”，也不是“全部类型都可以无条件从默认组件计算游戏机制”。尤其 `"minecraft:consumable":{}` **不能因为对象为空就等同于不存在**。

**⑨ 注册表：`26.3-registries/item/data.json`**

实际读取到 ID 列表，如 `"abandoned_camp_map"`、`"poplar_planks"`、`"straw_bed"`、`"baked_potato"`，**文件内部未携带 `minecraft:` 前缀**，需要依据注册表约定归一化成 `minecraft:<id>`。该文件有 **1,658 项**。它不是数值 network ID / 协议映射；不宜直接拿数组下标当网络物品 ID。

### B4. 真实存在但本次没有完整内容验证的高价值位置

这些路径**目录级存在已核实**，但除 B3 列出的文件外，不能给出“已验证所有内容”的结论：

- 方块 state / properties：`26.3-summary/blocks/data.json`（目录文件记录大小 303,902 字节）；可做注册表键与状态属性对照，但**不是碰撞盒的替代物**。
- 综合注册表：`26.3-summary/registries/data.json`（1,052,538 字节），与分拆 `26.3-registries/<registry>/data.json` 可独立比较，**本次没有穷举比较每个 registry**。

- 新增 26.3 的“燃料/烧炼效率”机制，官方发布说明还列出新 `minecraft:cooking_fuel` 组件；应优先调查实际默认组件，不能沿用过时“燃料 tag = 真相”的简化判断。

### C3. 哪些不能直接互相替代

- `minecraft-data` 的 **`recipes.json`** 是该工程自身的加工格式；不能直接当作 vanilla datapack JSON。若保留两源，必须独立解析后比较**语义等价性**。
- `mcmeta` **原始 `recipe`** 可作为 vanilla 规则事实；但实际“可否合成”还取决于玩家是否有原料/工作台/服务器是否覆盖配方。这些判断分别属于知识、状态与执行层。
- `mcmeta summary item_components` 和 `minecraft-data foods` 可能提供重叠信息；优先以**26.3 的原版默认组件**为一份事实来源，别同时存两个没有 provenance 的食物数值。
- `blockCollisionShapes` 是候选运行几何数据，不是 `mcmeta summary/blocks` 的同义文件；严格版本控制仍需单独校验。

### D3. 转换合同及不可丢失的语义

| 项目 | 输入 → 输出约定 | 必要诊断 |
|---|---|---|
| 路径与 resource ID | `data/<namespace>/recipe/<path>.json` → `recipe_id=<namespace>:<path>`；保留命名空间及路径层级 | `INVALID_ID`、`DUPLICATE_ID`、`UNKNOWN_NAMESPACE` |
| tag ID | `data/<namespace>/tags/item/<path>.json` → `tag_kind=item, tag_id=<namespace>:<path>` | `MISSING_TAG`、`TAG_CYCLE`、`TAG_INVALID_ENTRY` |
| bare ID | 源记录若按该 schema 使用短 ID（如 registries 的 `poplar_planks`），仅在**明示默认 namespace 的字段**补 `minecraft:`；不要对所有字符串通配 | `UNSUPPORTED_ID_FORMAT` |
| `#` 的上下文 | 原料字符串 `#minecraft:planks` 表示 tag；`key:{"#":...}` 中的 `"#"` 是 shaped pattern 符号 | `UNSUPPORTED_INGREDIENT` |
| shaped | 保存图案行数/列数/空位、symbol→ingredient 和结果 `count` | `INVALID_PATTERN`、`UNUSED_KEY`、`UNBOUND_SYMBOL` |
| shapeless | 材料 multiset / 序列保重数，**不做去重** | `EMPTY_INGREDIENT`、`INVALID_RESULT` |
| 递归 tag | 按 `kind + namespace + path` 递归；区分可选值 `required:false`（若存在）与真正缺失；循环检测 | `TAG_CYCLE`、`MISSING_REQUIRED_REFERENCE` |
| smelting / 其他加工 | 区分 serializer 类型、`ingredient`、`cookingtime`、`experience`、机器类型；未知 serializer **保留原始 AST** | `UNSUPPORTED_RECIPE_TYPE`（不静默丢弃） |
| loot | 存储 pools、entries、conditions/functions、概率与上下文；不压平成“固定掉落物” | `UNKNOWN_LOOT_CONDITION`、`MISSING_PREDICATE` |
| 默认 item components | 保存原始数据组件映射；区分**字段缺失**与 `null` / `{}` / `[]` | `UNKNOWN_COMPONENT_TYPE`、`COMPONENT_PARSE_FAILED` |
| 跨表引用 | recipe 产物/原料 → item registry；tag 值 → 对应 registry；默认组件键 → item registry | `UNRESOLVED_ITEM_REF`、`CROSS_VERSION_REFERENCE` |

**特别关注 26.3：** 官方公开说明含 `minecraft:cooking_fuel` 等新组件、新增蘑菇 tag、草床、Explorer Map 新物品。**不应先按旧版固化字段白名单再丢掉未知字段**。转换器应保存原始 JSON、schema 版本和一个 `unknown_fields[]` 诊断，不让未知字段在数据库里消失。

### D4. SQLite 最小结构合同（示意，不是要求现在改工程）

```sql
CREATE TABLE knowledge_release (
  release_id TEXT PRIMARY KEY,
  edition TEXT NOT NULL,
  game_version TEXT NOT NULL,
  manifest_sha256 TEXT NOT NULL,
  transformer_version TEXT NOT NULL,
  status TEXT NOT NULL,
  created_at TEXT NOT NULL
);

CREATE TABLE source_file (
  release_id TEXT NOT NULL,
  source_id TEXT NOT NULL,
  relative_path TEXT NOT NULL,
  resolved_commit TEXT NOT NULL,
  source_version TEXT NOT NULL,
  raw_sha256 TEXT NOT NULL,
  git_blob_sha1 TEXT,
  verify_status TEXT NOT NULL,
  PRIMARY KEY (release_id, source_id, relative_path)
);

CREATE TABLE knowledge_record (
  release_id TEXT NOT NULL,
  domain TEXT NOT NULL,
  resource_id TEXT NOT NULL,
  schema_version TEXT NOT NULL,
  normalized_json TEXT NOT NULL,
  source_file_key TEXT NOT NULL,
  evidence_status TEXT NOT NULL,
  PRIMARY KEY (release_id, domain, resource_id, source_file_key)
);

CREATE TABLE knowledge_diagnostic (
  release_id TEXT NOT NULL,
  code TEXT NOT NULL,
  resource_id TEXT,
  source_file_key TEXT,
  details_json TEXT NOT NULL
);
```

`knowledge_record` 允许**不同来源共存**以做冲突判定，不能用裸 `resource_id` 做 last-write-wins。正式生产可再拆 typed 表、FTS、索引；但优先保证**来源、版本、状态能审计**。

### D5. Coverage 合同

建议每次导入至少生成：

```json
{
  "target": "java/26.3",
  "source_commit": "538b2b167248c648b2198f2c0d56eced10dfc0cf",
  "discovered": {
    "recipe_files": 2042,
    "tag_files_all_kinds": 883,
    "loot_table_files_all_kinds": 1447
  },
  "imported": {
    "recipes": null,
    "tags": null,
    "loot_tables": null
  },
  "reference_integrity": {
    "missing_required": null,
    "cycles": null,
    "unhandled_types": null
  },
  "coverage_status": "NOT_YET_MEASURED"
}
```

这里的 `discovered` 计数来自本次 Git tree 读取，可作为**指定 source commit 的基准**；`imported` 和完整引用结果尚未真实跑过，所以只能是 `null`，**绝不填零**。最终要按 `item tags / block tags / entity tags`、各 recipe serializer、loot subtype、组件键分别统计成功/失败/未覆盖；全部失败记录要保留 path 和 source URL。

### D6. 知识发布必须 immutable

建议 `release_id` 由：

```text
sha256(canonical_json(
  target + sorted(source_file SHA256 list) + schema version
  + transformer commit + validation policies
))
```

计算得出。只要原始文件内容、映射规则或转换器任何一项变化，就产生**新 release**；不在旧 release 上就地补丁。一个查询必须绑定同一个 `release_id`，不能半途读到旧 recipe + 新 tag。对外展示「目标游戏版本」「source_version」「来源类型：原始/摘要/候选继承」「校验状态」。

建议查询约束如下：

```json
{
  "query": "minecraft:straw_bed",
  "target_version": "java/26.3",
  "release_id": "<actual-content-hash>",
  "domain": "recipe",
  "status": "verified_file_sample_or_imported_verified",
  "source_version": "26.3",
  "source_file": "data/minecraft/recipe/straw_bed.json",
  "source_commit": "538b2b167248c648b2198f2c0d56eced10dfc0cf",
  "result": {"count": 4, "id": "minecraft:straw_bed"}
}
```

这只是**接口契约示例**，没有声称当前 FurEverCraft 已经实现 `release_id` 或正式查询工具。

**不完整和冲突场景必须显式退化：**

| 状态 | 建议查询行为 |
|---|---|
| 26.3 文件未取到、未读、SHA 不匹配 | `source_unavailable` / `integrity_failed`，**不回退到 26.1 并伪装 26.3** |
| 在**确认全覆盖、无导入错误**的完整类别中查不到 ID | `not_found_in_verified_26_3_dataset`，允许作“该集合内不存在”断言 |
| 在尚未验证覆盖率的类别里查不到 ID | `unknown_due_to_incomplete_coverage`，而不是“26.3 不存在” |
| 候选继承数据未通过 26.3 差异校验 | `candidate_inherited_unverified`；可提供附来源的参考，**不可输出为确认的原版规则** |
| mcmeta 与 minecraft-data 候选冲突 | 返回 `source_conflict` + 双方 commit/path/字段，不静默选择某一个值 |
| 玩家服务器有 datapack 替换或实际观测矛盾 | **vanilla 规则保持不变**，另存 `server_observation/override`，含 server ID、首次/最后观测时间与证据 |
| Planner 查询当前背包、世界、容器状态 | 不从知识库猜测，返回需要 `world_state` / `inventory` / `server_observation` 数据 |
