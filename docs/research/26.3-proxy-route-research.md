## 0. 决策摘要（先给结论）

### 0.1 推荐路线、成立条件、拒绝条件

**推荐 A：两条 TCP socket 做真正的按序原始字节转发；以同一连接的只读、有限内存的旁路观察器解析关键帧和领域事件。** 不新建协议身份，不让 `minecraft-protocol.createServer + createClient` 代替玩家登录；原版客户端始终是唯一的真实玩家，控制仍走 Windows 输入。传输成功与观察完整性是两个独立状态；**A 的安全性可以优于它的可观测性，但不能把“游戏还能连接”误报为“世界状态仍然可信”。** `[I]`

**适用条件：**（a）客户端连接本地监听，代理拥有固定目标服务器映射；（b）代理到目标可建立相同 26.3 TCP 字节会话；（c）目标连接未协商代理不能解密的加密，或明确进入“仅转发、禁用自主观察控制”状态；（d）原始流在 handshake 特例以外不被变更；（e）观察器能在完整字节流上持续维护每向 frame、压缩和 phase 状态，在缺乏可靠控制事件时承认 `unknown`；（f）同一客户端重连产生新的 epoch，旧世界状态和动作全部 fencing。**未验证的条件（尤其是 26.3 真实原版互通、完整 item codec 与 registry）不是已经满足的事实。** `[I][U]`

**不能无条件声称 A 已可交付。** 对读不到的 26.3 组件，A 仍可把完整原始 bytes 转发给真正客户端，但只能将对应观察领域降级为不完整。若需求要求在该领域继续做可靠自动决策，就必须先补齐领域解析或采取可靠视觉/人工确认，不能偷偷假设旧版数据足够。**压缩/phase 的关键控制序列若已不可判读，观察侧不得扫描任意字节“同步”或假装恢复。** `[I]`

**候选 B（两端协议终止、全量解包后重封）不选为本期主线。** 只有真正需要替换/修改上行或下行协议消息、必须在两侧采用不同协议条件，且已经证明能在**不增加第二个玩家身体**的情况下正确复现 26.3 登录、身份、sessionId、动态 registry、config、各种协商、聊天与 keepalive/teleport ownership，才应重新评估 B。`createServer + createClient` 的普通示例并不满足这些条件，也不天然透明。现有上游源码甚至还保留了与 #1301 的 26.3 `sessionId` 字段不匹配的 server-side `success` 构造点。`[S][P][I]` 参考 [NMP server/login.js](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/server/login.js)、[minecraft-data #1301](https://github.com/PrismarineJS/minecraft-data/pull/1301)。

**结论级别：**架构选择已经可以做出；“26.3 旁路实现端到端无损解析”尚不能认证。不要为 A 实现暂停全部开发，也不要把其未知部分藏到“以后自动修复”。

### 0.3 最小自研清单（不是重写协议栈）

**必须写的“薄层”：** TCP listener/唯一上游绑定 + 连接 epoch；显式 target/hostname 映射和有条件的一次性 handshake 改写；两条真实 Socket 的流控、失败/半关闭处理；旁路的双向 packet-boundary 控制通道；按方向/阶段维护压缩与关键状态；观察域注册、背压与舍弃策略；领域归一化和 provenance/confidence/capabilities；session/body/维度/registry epoch fencing；观察故障告警和禁用危险自主动作的门禁；三角色 loopback harness。`[I]`

**不要重复写：** TCP 实现、可复用的 VarInt/ProtoDef 类型、完整 26.3 schema（在固定 #1301 数据基础上补缺）、现有 NMP native 读写器、已正确实现的 chunk palette/bitarray 基础、整个 Mineflayer、完整 prismarine-physics、另一种语言的长期运行时。`[I][S]`

**阻塞“宣称可解析”的材料**：① 把 **#1301 + #1538**（不是 #1539 两种 native 混装）封成单一固定消费版本，保存完成的 `data.js`/version mapping、`protocol.json`、依赖树与 Node22 的版本选择/解析测试结果；② 对 26.3 `sessionId`、config/known-packs/finish 及 PLAY→CONFIG 重配置获得分方向控制序列的可信独立 fixture；③ 对 #1301 的五项 `void` item-component codec 提供真实语义/数据，至少覆盖所需 inventory/item 类型；④ 对 chunk/light、`PositionPath` 和多 step entity move 保留样本来源以及长度/期望字段的外部 oracle；⑤ 对新增块和目标导航场景的 collision shapes 提供可靠原始数据与逐 state 测试。`[P][U]`

**不是阻塞架构定案、但阻塞交付验证的材料**：可复现三角色本地 fixture、受控原版 26.3 实机连接/重配置记录、实际握手 hostname 情况及加密分支、Windows 控制/客户端观察一致性。**不要求这轮下载 jar 或开真服**。完整 npm integrity/lockfile 由实施 Agent 在实际安装生成；此报告不伪造 checksum。`[I][U]`

## 1. A 与 B：什么能够被真正“透明”保留

### 1.1 A 在原理上能保留的内容

在上下游原样传字节、无加密改动且目标服务器协议兼容时，服务端发给客户端的 login `success/sessionId`、compression 通知、configuration registry/known-packs/settings/code-of-conduct 等选择与回应、PLAY 的 keepalive、teleport/confirm、签名聊天关联信息、AuthMe 类普通聊天指令，仍由**真实 vanilla 客户端和真实目标服务器**产生/消费。代理本身不构建 profile、不替客户端接受服务端条件，也不自动发 `finish_configuration`/keepalive 或虚构回执。**这是传输层透传的推论，不是每个 26.3 包已被 Observer 解出的证据。** `packet` 解码错误和原样 forwarding 成功允许同时成立。`[I]`

注意 known packs、resource packs、data packs 选择、server cookie、code of conduct 等消息中任一要求用户主动同意的含义，仍由**原版客户端交互**决定；本期代理不得在旁路“代替接受”。即使高层 NMP 默认会自动协商，也不允许作为行为捷径。`[I]`

**会推翻“透明”的条件**：TCP 上游被 server-side 中间件要求特殊 host、代理 IP 信任或转发头；下游填入 localhost 导致虚拟主机选路变化；协议版本不同、服务器侧转服/传输命令改变目标；服务器请求加密；游戏/代理采用应用级重新握手、重连而观察器继续复用旧缓存；任一环修改帧、重复发送、延迟业务包到超过协议 deadline 或丢字节。`[I]`

### 1.2 唯一许可的协议字节改写：handshake host/port（**可选，不是必然**）

原版客户端连接 `127.0.0.1:proxyPort` 时，Minecraft handshake 的 server address/port **可能是本地监听地址**，不是最终上游 hostname；目标是按用户预先配置的服务器地址建 socket，不是从这个地址猜测真正目标。原版上游未必关心 `serverAddress`，但虚拟主机路由、网络前置代理或服务端插件**可能**关心。故：

- **默认不碰握手包**。如果目标实测/明确协议配置确实要求原始虚拟主机，则通过 `targetAlias→approvedRemoteHost:approvedRemotePort` 的用户配置，从完整 handshake packet 解析 `protocolVersion`/host/port/nextState；仅改这一个包的 host/port 字段，再重算该**包**的长度 VarInt，其他 payload 原样、后续字节原样。
- 在 handshake complete 之前，此单次改写可以作用于 STATUS 与 LOGIN，但**绝不**解释为整个 session 做转码。不把 PROXY protocol、Velocity/Bungee 的 identity/IP 前缀“顺手加上”；那些可能要求服务端配置和专属信任/鉴权，本期不擅自伪造。
- 不允许根据任意 username/session 自行替换 UUID/profile。服务器真正看到的客户端 source IP 将是代理 socket 地址，这是不可避免的网络层差异；**原始转发保证的是应用消息字节，而非目标 TCP 四元组/IP 不变**。

`[D][I][U]` 关于 handshake 字段与 serverAddress 的历史行为可查 [Minecraft Wiki 协议数据](https://minecraft.wiki/w/Java_Edition_protocol/Packets)（不同版本细节以 26.3 固定 schema 为准）。26.3 原版使用本地地址时到底会携带什么 hostname **尚未在本轮实机证实**。

### 1.3 offline-mode **不等于**“永不加密”

`online-mode=false` 只对目标服务器通常的 Mojang 身份校验流程提供一种预期。实际要观察 **server→client LOGIN `encryption request`**（对应目标 schema 里的精确包名），若出现，并且后续 client→server 正常交换/启用加密，则 payload、连 packet length 都会成为密文；此时无私钥/密钥的只读旁路无法可靠分包和解析。**判断依据是实际握手包，而非配置名、IP、端口或服务器宣传为离线服。**`

处理规则：记录 `encrypted/unobservable` 及原因；禁止声称 `healthy`/`incomplete-but-still-readable`；可允许纯手动字节隧道保持连接，但**自动身体控制与以结构化世界状态为依据的任务必须暂停**。不加入 MITM、额外 bot、虚假 auth bypass。`[D][S][I]` 见 [Minecraft protocol FAQ](https://minecraft.wiki/w/Minecraft_Wiki:Projects/wiki.vg_merge/Protocol_FAQ) 和 [NMP `src/server/login.js` 对 `needToVerify` / `encryption_begin` 的分支](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/server/login.js)。

### 1.4 选 B 到底多出多少责任

B 在两端分别充当 server/client，需要独立处理 `LOGIN success(sessionId)` 及 profile/UUID（26.3 schema 新字段）、登录 acknowledge/配置完成、cookie/known packs、registry、keepalive、teleport 确认、position payload、settings/chat、可能的 account/auth 与 compression threshold。上下游不再只有一个 packet owner；丢包、自动回执和用户同意都要在 B 统一协调。NMP 内 `src/server/login.js` 会自主：决定身份、必要时发加密请求、发 `compress`、发 `success`、生成 registry、发 `finish_configuration`；`src/client/keepalive.js` 自动回 keep_alive。且 `success` 构造代码并没有 #1301 声称新加的 `sessionId`。**这一点单独就足以让“未经改动即是 26.3 透明代理”的说法站不住。** `[S][P]`

B 不是绝对不可做，而是要承担远高于 A 的 **protocol endpoint reproduction** 测试表面。当前产品明确只有同一个 vanilla 玩家；为 B 付出代价无对应利益。`[I]`

## 2. 传输、帧、压缩、解析：必须分清四种 Buffer

```text
TCP chunk（任意分片/合并，不是消息边界）
  ↓ 有状态 Splitter：读取 frame-length VarInt
完整 framed packet = VarInt(frameLength) | frameBody
  ↓ 去掉外层 frame length
frameBody（未协商压缩：packetId VarInt | packetPayload）
  ↓ 若 compression enabled：先处理 VarInt(uncompressedLength) 和可能的 zlib
未压缩 packet buffer = packetId VarInt | packetPayload
  ↓ 按 direction + protocol phase + 26.3 schema
packet typed object / domain projection
```

**源码证据：**NMP `src/transforms/framing.js` 的 `Framer` 用 `sizeOfVarInt(chunk.length)` 添加外层长度，`Splitter` 按声明长度推出 **不带外层 length** 的 Buffer；`src/transforms/compression.js` 的 compressor 对未压缩 packet buffer 生成压缩子头（零或原长）与 zlib 数据；`src/transforms/serializer.js` 在特定 phase/direction 上建 `ProtoDef` parser。`[S]` 固定源码：[framing.js](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/transforms/framing.js)、[compression.js](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/transforms/compression.js)、[serializer.js](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/transforms/serializer.js)。

**`Client.writeRaw(buffer)` 不是 TCP 原样转发。** 源码通过 `this.compressor === null ? this.framer : this.compressor` 写入，接下来仍加外层帧长、可能再加压缩标头。这一 API 接收的是**未压缩 packet buffer**（通常包含 packet ID），**不是完整 frame**，更不是 TCP chunk；不能把上游原始 framed bytes 传给 `writeRaw`。`createSerializer`/`createDeserializer` 是源码明确从 `src/index.js` 暴露的 API；`framing/compression` 依赖内部路径，需锁定 commit 或转成小型隔离 adapter，**不能承诺它们具有长期公共 API 兼容性**。`[S]` 固定代码：[client.js#writeRaw](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/client.js)、[index.js](https://github.com/PrismarineJS/node-minecraft-protocol/blob/a1a33809c49553e544a7efd3d8bc03eb0867f4ab/src/index.js)。

**底层可复用策略比较：**

| 方案 | 兼容自动插件？ | 优点 | 风险 | 选择 |
|---|---|---|---|---|
| 单独组合 `framing + compression + createDeserializer`（不创建 `Client`） | **不加载** client/server login/config/keepalive 插件 | 最大限度复用 ProtoDef 编解码，无第二协议 endpoint；符合观察只读角色 | framing/compression 是内部模块；必须自己管 phase、压缩切换和资源限制 | **首选**（将内部依赖封在一个 adapter，固定代码来源） |
| 独立实现极薄 packet frame observer（只做 VarInt/frame/解压），typed packet 仍交 ProtoDef | 不加载 | 更好控制有界内存、frame counter、压缩异常和跳过策略 | 要额外验证自家 framing/压缩和上游一致，不要复制整个 codec | **若内部 Transform 的 buffer 拷贝和异常策略不适合旁路时使用** |
| 将 NMP `Client` 作为被动 TCP 嗅探器 | 可以不用 `createClient` 高层插件，但 `Client` 自己设 socket/pipe | 现有 `Client` 已串好 transforms | 可能抢 socket 流和 phase ownership、`setSocket` 事件状态、双消耗问题；没有透明旁路保证 | **不优先** |
| 固定维护最小 native codec 补丁/适配包 | 不加载高层 | 允许 `entityDelta` 和 schema 达成可运行闭环 | 版本、生成缓存、type registry 分裂 | **仅限实际发现的差异** |
| Fork 整个 NMP/minecraft-data 生态、从头协议栈 | 无 | 控制理论上最大 | 升级与测试表面远超需求 | **不采用** |

低层 frame/reader 在观察通道可以解包，但**永远不要让其输出的重新编码 Buffer 进入 A 的游戏传输通道**。真实传输依赖 socket 的原始字节源，观察器只拿派生副本或有限引用。`[I]`

## 3. 双向 phase / compression / packet ownership（生产实现必须按本表落账）

**状态键**：`connectionEpoch` + `direction(C→S/S→C)` + `phase` + `compressionMode` + `registryEpoch`。phase 可以在两方向处于短暂不同的可信边界，不能只有一个全局 Boolean `inPlay`；同一方向内的包顺序才由 TCP 保证，跨方向相对到达顺序不构成总序。`[I]`

| 边界 | 实际 owner（A） | 观察器可以做什么 | 状态更新/风险 |
|---|---|---|---|
| C→S HANDSHAKING `handshake`/intention | 真客户端生成，真服务器消费 | 解 VarInt protocol 777、host/port、nextState；在**明确配置**下可唯一改 handshake | C→S 进入 STATUS/LOGIN；serverAddr 不能推断 remote host；改写需重算 frame-length |
| STATUS 双向 request/response/ping/pong | 客户端和上游服务器 | 记录版本/MOTD/延迟信息 | **不**由本地 NMP server 自动回复；状态流可由上游决定结束；状态连接不复用为 LOGIN |
| C→S LOGIN `login_start` | 原版客户端 | 记 username/协议观察事实（不要臆造 UUID） | identity context 属真实上游；代理不生成第二 profile |
| S→C LOGIN `encryption request`（若出现） | 真服务器请求，真客户端回应 | 标记加密协商，立即降级 observation | 见 §1.3；**不**因 offline-mode 就假定不会出现 |
| S→C LOGIN `set_compression` | 真服务器发送，真客户端配置 | 读 threshold 并登记压缩切换控制事件 | 同一 S→C 方向在本完整帧**之后**压缩；C→S 切换要考虑客户端接收因果与在途旧包，不能以墙钟时间排序两条 TCP 流 |
| S→C LOGIN `success`（含 26.3 `sessionId`） | 真服务器 | 提取 session/account 标识（隐私最小化）；验证包结构完整 | 若 schema 偏移，应仅降级对应解析，不要让代理构造 success；下一阶段由客户端 ack 与服务器共同推进 |
| C→S LOGIN `login_acknowledged` | 真客户端 | 记录实际发包 | 关联 CONFIG 过渡；在压缩前后切换边界未证实前设 `ambiguous` |
| S↔C CONFIG: known packs / packs / registry / features / cookies / settings / code-of-conduct 等 | 真客户端与真服务器 | 只观察 Registry/pack 内容和客户端明确选择 | 不能默认接受；packet ID 必须取 #1301 修正表，26.3 `post_effects` 改动影响相邻 ID |
| S→C `finish_configuration`；C→S 相应确认 | 分别由服务器和客户端 | 记录双向完成、同步 registry epoch | 各方向分开更新 PLAY parser；先后到达存在非原子窗口，旧 parser 不得误读另一阶段 |
| PLAY S→C initial login/respawn, chunk/light, inventory, health, entities, chat | 真服务器 | 对**有证据的领域**解码为 projection | `onlineMode` 新字段、item components、light/PositionPath 等按 26.3 schema；失败按领域标 incomplete |
| PLAY C→S 控制/聊天/点击 | 真客户端，经 Windows 键鼠触发 | 只观察 outbound intent 和后续 server authority | AuthMe 登录注册属于真正客户端聊天；不得代理自动代答，也不能把传出 packet 当确认结果 |
| PLAY keepalive 及响应 | 上游服务器请求，真客户端响应 | 关联实际 ID 和 round-trip | 本地 NMP `client/keepalive.js` 自动回 keep_alive 的插件**不可启用**；代理不能替客户端回复 |
| PLAY S→C teleport/position correction；C→S `accept_teleportation` | 真服务器修正，真客户端确认 | 记录 ID/目标 x,y,z、旋转和 ack；使 motor generation 失效 | #1301 指 26.3 serverbound confirm 附带 x/y/z/yRot/xRot，不能按老字段假定；纠偏依服务器事实 |
| PLAY→CONFIG reconfiguration，完成后回 PLAY | 真实双方各自的协议端点 | 更新 phase/registries，并对使用旧 registry 的投影失效化 | 不能要求重连才识别；控制序列的精确 ID/字段**仍需固定 26.3 schema 与独立 fixture 验证** |
| disconnect / socket half-close / reconnection | 真实 socket 生命周期 | 记录 reason、释放输入 held-set、结束观察 epoch | 旧传输 epoch 的迟到解包结果、模型输出、动作计划一律 fencing；新会话不继承“可信当前状态” |

**特别说明：**#1301 证明 `login.success.sessionId` / config `post_effects` 与 teleport confirm 是真实的 26.3 增量；其他行里采用的通用阶段名称是**语义描述**，不是保证 `packet.name`/ID 在每条目标分支中恰好同名。对 phase 切换、是否存在某一客户端方向的独立 ack，以固定 schema 和独立样本确认，不能照表机械地调用 `client.write()`。`[P][I][U]` [#1301 明细](https://github.com/PrismarineJS/minecraft-data/pull/1301)。

### 3.1 压缩切换中的细微竞态

若监听到 S→C `set_compression`，可以明确 S→C 的**后续字节**该按压缩 framing 解析；但 C→S 的压缩切换发生在客户端**收到该通知后**。两条 TCP socket 的“代理观察先收到哪一向字节”不等于真实两端的处理先后。特别是已经在途的 C→S 字节可能晚于代理观察到的 S→C threshold 帧。不能仅调用一个两向共享 `compressionEnabled=true` 即宣称绝对无歧义；在 LOGIN 常规预期序列中可用 phase-specific 合法包、显式因果 barrier/接收回执和明确的 packet grammar 验证，无法判定时把窗口标为 `compression_pending/ambiguous`，在控制锚点完成前不产出权威事件。`[I][U]`

### 3.2 世界状态所有权

| 状态 | 唯一写入者 | 何时失效 | 允许下游使用 |
|---|---|---|---|
| Transport sockets & flow | socket-pair coordinator | 任一连接结束 | 游戏仍可正常通信，和观察正确性独立 |
| C→S 与 S→C frame parser | 每向轻量 tracker | bytes 丢失、frame size 不可信、epoch 变更 | 只能声明“frame 信心”，不自动传递领域正确性 |
| Compression mode | 每向 negotiation tracker + causality state | 协商不清、加密触发、epoch 变更 | 需要明确控制帧/安全过渡 |
| Phase | 每向 phase tracker | 不可识别状态跃迁、重连 | 不可直接复用高层 NMP 的外部 state 字段 |
| Dynamic registry/capability | registry projection manager | PLAY→CONFIG、维度/会话切换、数据包缺失 | 以 registry epoch、世界键作用域读取 |
| Chunk/block/light | world projection manager | unload、改变、缺包、世界/维度切换 | 根据 coverage/age/shape confidence 检查 |
| Entity trajectories | entity projection manager | entity remove/respawn、缺包、时序断裂 | entityId+spawn generation；仅完整观测的轨迹可信 |
| Inventory/windows/components | inventory projection manager | window change/state mismatch、unknown component | 失效子窗口/物品，不能静默移到下个组件 |

| Motor / Planner | Runtime/Executor（不写协议 owner） | generation/fencing/抢占/失败 | 不直接操作 socket，不以预测作为 server authority |

## 4. 有界旁路：失败隔离、恢复能力与流控

### 4.1 正确的队列边界

**主通路** `clientSocket → upstreamSocket` / `upstreamSocket → clientSocket` 仅存放由 socket 背压控制的、有上限的在途字节，调用 `write` 后按 `drain` 调节 `pause/resume`，设置 timeout/内存/写缓冲硬界限；超限可断开受控连接，不能无限排队。严禁在主通路同步 zlib、NBT、chunk、entity parse、模型调用或 SQL IO。`[D][I]`

**观察旁路** 不应直接把无界 `TCP chunk` 复制给异步大队列：TCP chunk 任意分裂，丢任意几字节可能永久损坏 framing。推荐在接收事件中做严格限额的 frame boundary tracker（只做增量 VarInt/frame 缓存和少量关键控制 packet ID，拒绝畸形巨帧；约束 CPU/buffer），在它后面才投递完整 frame 给有界的语义工作队列。对于 chunk/NBT 之类重包，保留 frame 元数据和必要控制投影，**有意识地跳过**高成本领域解码并标记该领域 `incomplete`；压缩 frame 如需先 inflate 才知包 ID，inflate 要异步/受时限和压缩比/声明原长上限约束。不能因为便宜的 framing 在接收 callback 中运行，就允许同步大包 zlib 在热路径里执行。`[I]`

**旁路预算不足时二选一：**继续 socket passthrough，Observer 降级 `unreliable/disabled` 并禁用需要结构化状态的自动动作；或为了产品要求的观测质量由策略主动断开/重连受控会话。**不能**把未处理的字节随意丢掉后继续假装 parser 仍同步。即使某领域被明确跳过，也仍需在必要时维护 registry/phase/compression 所需的控制通道。`[I]`

### 4.2 失败与恢复矩阵

| 事件 | TCP 转发 | framing | phase/compression | 领域可信度 | 是否可在同一连接恢复 |
|---|---|---|---|---|---|
| 某个完整、非控制 packet 的 typed parse 失败，但 frame 已知 | 继续 | 仍可知 | 若不影响控制，保留 | 该领域/依赖它的投影 `incomplete` | 可；下一个完整 frame 仍有边界，领域需新的权威快照 |
| 有效完整 frame 含未知 packet ID，且属于非控制类 | 继续 | 仍可知 | **若不能确定是否控制包则 unknown** | 未知领域/关联状态失效 | 仅能可靠排除控制影响时局部恢复 |
| item component unknown/unimplemented `void`，长度无法知 | 继续 | 仍可知 | 其它帧控制可继续，但当前包不能向内“按字段跳过” | 当前 item/window 及有关槽位 incomplete | 是；从下一个 **frame 边界** 恢复，窗口需刷新 |
| Chunk/light 解析异常（未破坏 packet frame） | 继续 | 仍可知 | 保持 | 相应 chunk/light/导航区域失效，不把缺块当空气 | 是；后续权威 chunk 全量包或特定完整更新恢复 |
| 领域工作队列超预算，完整帧主动跳过 | 继续 | 仍可知 | 只有独立关键控制通道没丢才可信 | 被跳过领域失效 | 可有条件恢复；要防止依赖旧状态计算 |
| frame length VarInt 截断但后续字节可能到达 | 继续 | `pending`，只可短期缓存 | 等待完整 frame | 等待 | 在限时/限额内补齐可以；超界后不能靠字节扫描 |
| frame length 畸形、超上限、观察 buffer 中丢字节 | 继续（可按政策断开） | **unknown** | **unknown** | **全域不可信** | 一般**不能**，只能新连接/有可信的外部 framing 锚点；无“找下一个 0xXX” |
| set_compression/控制 frame 丢失或顺序不可证明 | 继续 | 外层若未加密可尝试保持，但 packet 语义未知 | **unknown** | 全局/依赖域失效 | 不能声称随后猜测成功；需独立可信控制锚点或重连 |
| PLAY↔CONFIG 切换事件未识别 | 继续 | 可能仍知 | **phase unknown** | 依赖 phase 的全部包失效 | 只有独立可信状态锚点才能恢复；通常重连 |
| encryption 协商完成 | 转发可继续 | 后续密文不再能观测明文 length | **encrypted/unobservable** | 全部结构化域失效 | 不可在本连接被动恢复，不进行 MITM |
| rejoin、respawn、dimension change | 正常 | 重新初始化或继续对应会话解析 | 重新关联 epoch/phase | 旧世界 key/registry/state fencing | 通过新的权威包恢复；不复用旧当前状态 |
| 代理 crash/重启 | TCP 中断 | 清空 | 清空 | 清空 | **新连接**；不得宣称同一 socket 上热恢复 |

**三条红线：**TCP chunk 不是 packet；不能靠扫描字节中貌似合法的 packet ID 同步；某一个 buffer `writeRaw` 成功不是正确重建另一条 TCP 字节流。`[I][S]`

### 5.2 为什么推荐 `entityDelta` 一套（而不是把两个都引入）

**选 #1301 的数据 schema + #1538 的 `entityDelta` 原生类型这一对。** #1301 `packet_rel_entity_move.move` / `packet_entity_move_look.move` 已引用 `entityDelta`；#1538 fixed code 在 **interpreted `minecraft.js` + compiled `compiler-minecraft.js`** 双侧注册了 `read/write/sizeOf`，返回统一 `{onGround, steps:[{dX,dY,dZ,ticks}]}`。这样追随当前已经对齐的上游 stack，最少修改 NMP/data 的交界。`[S][P]`

`vecDelta`（#1539）有独立较强的**据作者称取自原版**的十六进制回归向量和 interpreted/compiled 单元测试，具参考价值，但数据形状是 linear 时 `{onGround,dX,dY,dZ}`、stepped 时 `{onGround,steps}`；它并非可与 `entityDelta` 任意互换的符号别名。GitHub 显示 #1539 closed but **not merged**；其 codec/fixture 更适合作为 #1538 方案的对照 oracle，**不同时注册成另一套线上契约**。`[S][P]` [#1538 review 指出互斥](https://github.com/PrismarineJS/node-minecraft-protocol/pull/1538)、[#1539 PR](https://github.com/PrismarineJS/node-minecraft-protocol/pull/1539)。

**必须纳入验收的一处字节保真风险：** #1538 `writeEntityDelta` 在 `steps.length===1 && steps[0].ticks===0` 时把它**规范化成 linear 变体**，但 #1539 的独立向量有 `stepCount=1, ticks=0` 的合法 stepped packet：`0200000100020003`。语义值看起来一致，重编码字节却未必一致，且 PR reviewer 已指出该差异。因此**不能**拿 `entityDelta` 解码→编码替代 A 的 raw passthrough，也不能只测 roundtrip 意义而不测原始样本字节等价。`[S][P]`

**PositionPath 则不是 `entityDelta`。** 前者属于 `sync_entity_position` 的绝对 xyz 路径（linear/stepped，含节点时间信息）；后者属于 `rel_entity_move` / `entity_move_look` 的相对位置增量。统一领域轨迹时把两种消息分别归一化为 *absolute anchor* 与 *relative trajectory*；不能直接累加 PositionPath 当相对 delta。`[P][I]` [#1301](https://github.com/PrismarineJS/minecraft-data/pull/1301)。

## 6. 离线最小验证规格：四层必须分开证明

统一三角色 loopback：`TestVanillaPeer (独立下游 socket)` → `FurEverCraft TCP proxy` → `TestUpstreamPeer (独立上游 socket)`。可复用上游不同解析器/保存在仓库的黄金数据；**不能只把同一套 codec encode 后自己 decode 就说“原版兼容”**。本期仅设计规格，不执行或连接真游戏。

| 验证层 | 输入与步骤 | 必须断言 | 不能由该层声称 |
|---|---|---|---|
| **T1 传输等价** | 任意 TCP 分片/合并、随机有界负载、两向半关闭、队列突发；测试 STATUS/LOGIN/CONFIG/PLAY 原样字节流 | 双向目标收到的串联 byte sequence 与源一致；拆包/合包、drain、close、timeout 行为确定；允许经明示的 handshake 唯一变更，且预期后续 stream 全等 | 不证明 Minecraft 语义/26.3 packet 合法 |
| **T2 协议 framing/解压** | 外部构造已知 VarInt frame、不同 compression threshold、零原长、非法数据、控制边界、pending buffer | 每个 frame 消耗字节数与原始长度一致、packet ID/phase/direction 正确；出错不会串包；byte-level drop 使全局 unknown | 不证明整个 item/chunk 业务解释正确 |
| **T3 领域归一化** | 已固定 26.3 golden vectors：entity delta/PositionPath、slots/components、palette/light、position correction、registry 控制 | 明确 `{source,epoch,phase,serverTick?,confidence}`；与**独立 oracle** 对照字段值、字节长度、时间/空间单位，错包按领域失效 | 无法证明真实原版互通、Java/Windows 输入有效 |
| **T4 原版真实互通（留待实施）** | 受控 vanilla 26.3 客户端 offline server 的状态/聊天/登录/重配置/移动/退出多情景 | 实体客户端是唯一玩家；AuthMe 手动行为、pack 同意由客户端负责；网络原始字节转发一致，结构化观测符合服务器真实状态 | 不能在本次静态研究期间宣称已完成 |

**T1 必须覆盖**：Handshake mapping off/on（把唯一重封包单独比较）；随机 TCP split 发生在 VarInt 内、frame 体内、两个连续包中间；1 字节 1 chunk 和多包同 chunk；双向数据同时达到限额；停滞 downstream/upstream；OBS worker 停止/异常/超载；PLAY↔CONFIG、registry 重置；跨 epoch 重连；与 observer 引擎无关的游戏 byte equality。`[I]`

**T2 必须覆盖**：compression threshold 触发边界、压缩前后同一接收 buffer 的相邻帧；非法/超大的 `uncompressedLength`、截断 zlib、过大压缩比、非法 packet ID/未知控制 ID；任意 HTTP/Java 网络 TCP chunk 到达顺序不能改变同一方向的 frame 顺序。跨方向压缩竞态要由明确控制时序测试，不能写一段单线程串行 fixture 就算完成。`[I]`

**T3 必须覆盖**：步进 relative `ticks=0`/`>0`/跨 VarInt 边界、PositionPath absolute；二进制 item components 中有未知 component 的整包 fail-safe；chunk light masks 零、跨 8/64 bit、高位、空数组与 nonempty；位置修正与 confirm 的 ID/xyz/yRot/xRot；相关 domain 的 snapshot / unknown / recovery。`[P][I]`

## 7. 与 FurEverCraft 当前代码的接线边界

附带的 `FurEverCraft-source-first-look-2026-10-17.md` 确认：远端 `main@2cd72cec945298bc86d5be5df9b66493ce066c6f` 的 `src/bridge/protocol/session.ts` 只做固定 1.20.4/765 `createSerializer/createDeserializer`、内存 LoopbackByteTransport 与简单 VarInt **无压缩**；尚无 TCP 代理，更没有已运行的高层 terminating proxy。`src/execution/factory.ts` 的 profile 大多仍指向 FakeClientBridge；Bridge 仍是二维/同步假设，SessionRuntime 直接引用 Fake 类型；同时另有 Executor `ambiguous→succeeded` 误写路径和跨 epoch 历史对账限制。`[用户提供源码初读；未重新全仓复核]`

因此此处不是“从已经投入使用的 B 迁移到 A”。是**给未落地的真实协议桥选择生产路线**：保留能复用的 ProtoDef adapter、SQLite/工具路由/执行骨架，但使 `ClientBridge` 与 Runtime 具备三维位置、真实状态来源、异步动作合同及 generation 控制。后续规划可以并行梳理执行合同问题，**本报告不把这些工作扩写成完整产品实施计划**。`[I]`

典型生产连接顺序（描述性，不是可直接运行的实现）：

```text
Configure remote endpoint + local port
  → Listen localhost
  → Vanilla Java 26.3 connects (real body)
  → One upstream TCP connection (same session)
  → Bidirectional raw bytes immediately forwarded with bounded backpressure
  → Passive two-direction tracker observes COMPLETE frames/control events
  → Domain adapters update epoch-scoped world/body projections only when valid
  → Planner/Skill/Motor consume checked projections; Motor sends Windows input to real client
  → Real client emits ordinary serverbound packets; server replies; Observer updates result
```

运行中允许 `transportHealthy && observerDegraded` 的短暂情况，但 UI/CLI 必须如实显示**观察不可信及自主动作受限**。重连时目标服务器/profile 不得从旧登录结果默默填充新身份；世界记录可以留作历史记忆，但不再当作当前可见世界。`[I]`
